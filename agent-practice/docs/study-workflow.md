# 从学习到求职的执行流程

本流程服务前端开发者转向 Python、AI 应用和 Agent 开发。主要目标是能独立完成项目、解释设计并应对代码与场景面试。每天可投入约 2–4 小时，也可以只完成一个短学习段；完成时间和掌握程度分开记录。

[路线图](roadmap.md)给出全部主题和阶段成果，[当前计划](current-plan.md)给出眼下该做的事，[进度文件](../progress.json)和[反馈历史](reviews.md)记录实际证据。D1–D56 是主题编号，不对应自然日，也不因题面已生成就算学完。

## 每次开始前

1. 打开[当前计划](current-plan.md)，确认当前主题、前置能力、要完成的项目增量和验收用例。若计划与用户的新目标或可用时间冲突，先按最新信息调整本次安排。
2. 打开对应题目源文件。题目要求、必要语法速查、输入、期望行为、边界用例、代码区和“作答记录”放在同一文件；无需在独立答案文件中作答。
3. 动手前尝试说明输入、输出和可能失败的边界。如果是输出预测题，先写预测，再运行；不要用运行结果冒充预测。
4. 运行当前入口，读懂错误，再修改代码。基础 Python 题可在项目目录用 `py -3 -B exercises\day01\task_info.py`；没有 `py` 时用 `python -B exercises\day01\task_info.py`。后续题目以各自文件中的实际启动方式为准。

换聊天后，助手先读取本地进度、计划、反馈和相关代码，再继续教学；不用用户重复叙述已记下的背景。如果助手无法访问本机文件，则根据用户提供的材料批改，并明确哪些本地进度无法写回。没有后台监听或自动同步。

## 一轮学习怎么分段

| 学习段 | 做什么 | 参考用时 | 完成标志 |
| --- | --- | --- | --- |
| 前置与理解 | 看本题顶部讲解，用 JS/TS 对照理解新的 Python 写法，预测正常与一个边界输入 | 15–25 分钟 | 能说出要处理什么，不靠照抄完整答案 |
| 实现 | 独立完成一项综合任务或项目增量；工作打断时保存当前代码和具体卡点 | 30–60 分钟 | 代码能运行或留下可定位的错误信息 |
| 变式与排错 | 用题内正常、边界和错误用例运行；修改一个输入检查是否写死结果 | 20–40 分钟 | 记录真实结果，解释至少一处修正原因 |
| 口述与反馈 | 用自己的话讲输入、关键分支、失败处理和取舍；请助手检查 | 10–20 分钟 | 获得针对性反馈和下一次安排 |

这些时长可拆到工作间隙，不用为凑满 2–4 小时增加重复题。已熟悉的前端知识经短诊断即可压缩；新知识缺前置时先补最小必要内容。重点放在“一项需求 + 多组输入 + 一次解释”，避免机械刷同构题。

## 作答与求助

代码写在题目文件的代码区，预测、解释、运行或变式结果写在该文件的“作答记录”注释区。按本题要求填写关键项即可；助手能直接运行核对的输出不必逐行抄回聊天。跨文件项目以题目入口文件指明要改的文件和验收方法，作答记录仍集中在入口文件。

做完一部分就可说“检查我当前这题”或“综合任务完成了，检查代码”，不用等整阶段结束。报卡点时指出具体输入、实际输出或报错，以及你原本期待的结果；没有运行就如实写未运行。助手先定位问题并给一小步提示，仍卡住时改用 JS/TS 对照或更小的变式。只有用户明确要求完整答案时才提供。

练习代码和已有作答由用户保有；批改默认不覆盖用户文件。初始骨架能启动、读过讲义、助手运行通过某个临时示例，都不能替代用户完成题目。涉及依赖安装、密钥、模型调用成本、公开部署或 Git 提交，遵守项目约定，不随课程自动执行。

## 每次批改后如何更新路线

助手按[反馈规则](feedback.md)依次查看代码、运行证据、解释与变式，给出具体结论，再更新[进度文件](../progress.json)、[反馈历史](reviews.md)和[当前计划](current-plan.md)。用户不用自己编辑 JSON。每项结论写清楚证据来源：实际运行、用户提供的输出、静态检查或未验证；运行骨架和检查者生成的答案不能记作用户掌握。

| 观察到的结果 | 下一次安排 |
| --- | --- |
| 独立实现且正常、边界输入通过，能解释关键选择 | 进入下一项综合需求；相邻主题可合并，重复题经记录后免做 |
| 程序能跑，但只在固定数据下正确 | 换一个输入或需求，先解决写死结果与边界问题 |
| 参考了提示或答案才完成 | 保留当前成果，下一次给一个不带答案的新变式复测独立性 |
| 同一概念连续两次卡住 | 换讲解角度，缩小任务，只补阻塞后续的一点 |
| 只是标点、空格或重复抄写问题 | 作为改进建议记录；当格式是接口契约、字段类型或明确业务要求时按契约验收 |
| 学习中断后回来 | 用 5–10 分钟复查上次卡点；通过就继续，不从头重做 |

每次只详细排下一项与紧邻的一项。阶段目标可以提前完成，但跳过的能力需要对应诊断证据，不能把一批未做主题直接标成已验收。学习耗时未知就留空，不用估算。

## 阶段验收与求职材料

每阶段以可运行的项目增量验收：基础脚本、命令行任务管理、API 与数据库、全栈联调、模型聊天、工具执行、可靠性、权限及演示作品，具体范围见[路线图](roadmap.md)。验收至少覆盖正常输入、关键边界、一次独立变更和一处实际排错。跨阶段借用新知识时分别核对覆盖能力，不因做了项目就自动把所有主题判为通过。

从第一阶段起，每次保留一句口述材料：“要解决什么问题 → 为什么这样实现 → 用什么输入验证 → 还有什么限制。”进入后端阶段后，能讲清请求如何到达数据库、类型与权限如何校验；进入 Agent 阶段后，能讲清模型输出、真实工具结果、写入确认与失败回退的区别。作品集使用真实代码、可复现步骤、实测结果和已知限制，不编造指标。

目标岗位描述一旦明确，按其职责调整项目深度与面试练习：Python 后端侧重 SQL、测试、异步与权限；Agent 应用侧重工具、评估与可控执行；AI 全栈增加界面联调和用户操作流程。扩展 RAG、MCP 或框架前先完成相应基础能力，再用一个可解释的最小实例验证。

最终演练是让一个未看过代码的人按 README 启动应用，再完成一次真实需求改动和关键回归；学习者用约 3 分钟介绍项目，并回答实现取舍、失败案例及下一步改进。若其中一项不能独立完成，把它写进进度与下一次计划，继续练对应能力，不用重排整条路线。
