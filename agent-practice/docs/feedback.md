# 每次反馈、验收与动态调整

用户每天约有 2–4 小时，在工作间隙学习，主要为转岗求职和面试。按 25–40 分钟左右的学习段组织；不把可用时长当成必须完成的作业量。
普通单元从 2–4 道诊断或基础题、1 个项目增量和 1 次简短解释开始；结果不理想时减量拆分，掌握后减少重复题。原有 D1 的 8 题保留作为题库。
每阶段保留能力验收，当前安排以 [当前计划](current-plan.md) 为准。
当前用户已反馈基础题偏简单，后续优先“一项综合需求 + 多组边界输入”，把相邻主题按前置能力合并。原题已核实的计算、变量和状态逻辑不因冒号、空格或重复抄写被判为未掌握；未核实的解释能力在综合任务中复查。

## 提交格式

```text
D1
已完成：第 1—4 题
代码位置或片段：可直接请求查看本地文件
运行结果：粘贴输出，或注明未运行
卡点：具体哪一行或哪个概念不理解
实际用时：分钟数
是否参考提示或完整答案：说明独立完成的部分
下次时间和精力：可选
```

可以分批提交，不用全部做完才反馈。
每题的完整要求、代码及全部作答统一位于同一个 `.py` 文件，预测、解释、实际输出和变式结果填写在该文件明确列出的“作答记录”注释项中。批改读取该文件即可，不要求用户在聊天重复粘贴结果，不再生成独立答题文件。

## 验收标准

1. 程序能运行，输出符合题目要求。
2. 修改输入数据后仍然正确，不靠写死结果。
3. 能说明关键变量、语句或调用链。
4. 项目任务达到当天列出的要求。

只读过题目或运行未完成的骨架，不代表已经掌握。
面试准备增加一条：用自己的话解释一处实现或排错过程，不要求背术语。解释可以通过聊天提交；基础作业跑通不等于面试已准备充分。
遇到卡点，先讲清一个原因，做 1–2 道针对性变式后复测；同一概念连续两次仍卡住则改变讲解方式，不自动堆题。
状态可使用：未开始、学习中、待验收、需补练、已验收。

## 每次学习反馈后的执行顺序

1. 读取本地进度、当前计划、历史反馈和本次代码。用户已提供过的背景不重复询问；本次时间未知时不估算实际耗时。
2. 核对代码、运行、关键解释及变式证据。基础脚本可在安全条件满足时运行；记录命令和结果。需要依赖安装、模型调用、密钥或业务写入时不自动执行，说明当前能验证的范围。
3. 给出针对性反馈：具体做对什么、错误原因、先给哪一步提示。默认不覆盖用户代码，不代写整份答案。
4. 更新 `progress.json` 和 [反馈历史](reviews.md)，然后重写 [当前计划](current-plan.md)。同一轮提交的补充不重复计数，新的作答尝试另记一次。
5. 回复中说明结论、证据、尚未验证内容和下一次安排。规则调整不等于学习通过。

仅问概念时正常解释；只有获得足以判断的新证据才更新掌握结论。粘贴代码与本地版本不同则标注来源，不擅自覆盖本地文件。

## 如何决定下一次安排

| 观察到的证据 | 判断与调整 |
| --- | --- |
| 独立完成核心任务、解释正确且新数据变式通过 | 对应技能记为“可独立”，压缩同类题；前置能力齐备后进入下一单元 |
| 题目在提示后完成，或参考过完整答案 | 记为“需提示”；下一次先做一个不带答案的变式，再判断是否掌握 |
| 程序正确，但解释不清或变更输入后失败 | 暂不验收；补原理解释和变式，不用整套题重来 |
| 概念错误阻塞后续，或同一错误反复出现 | 记为“需补练”；缩小任务，回到最近未掌握的前置能力，用 JS/TS 对照后复测 |
| 仅自述完成、只有静态代码，或缺少关键运行证据 | 已提交部分记为待验收；允许反馈代码问题，但不记为整体运行通过 |
| 实际用时长、工作打断或精力不足 | 先区分时间和理解问题，拆成更小学习段，不仅凭用时降低能力评价 |
| 已有前端知识经短任务验证 | 可合并联调主题，仍保留跨数据库、接口、页面的独立字段变更验收 |
| 间隔后继续学习 | 用 5–10 分钟旧卡点或变式复查；正确则继续，失败仅补相关前置 |

复习安排按后续实际学习触发：下一次开始时短复测，之后的阶段验收再混合复查，不设后台日历提醒。
已通过的技能后续出现反例时可以降回需提示/需补练，保留先前记录并说明原因；阶段任务失效时同步调整验收状态。

## 进度文件约定

`progress.json` 是当前事实摘要，`reviews.md` 保存详细历史，`current-plan.md` 保存下一步可执行安排。助手根据实际反馈维护，用户不必编辑 JSON。

| 字段 | 含义与更新规则 |
| --- | --- |
| `schema_version` | 当前为 2；保留原有字段，新增能力和反馈记录 |
| `learner_profile` | 用户确认的背景、目标与可用时间；推测岗位必须注明待确认 |
| `total_learning_days` / `planning.baseline_topics` | 都为 56，表示参考主题数，不是已学习天数或完成期限 |
| `current_day` | 当前处理的主线主题编号；补练保持原编号，压缩或合并时记录原因 |
| `days.dayNN.status` | 未开始、学习中、待验收、需补练、已验收之一 |
| `completed_questions` | 确有作答并核对正确的题号；免做题另记 `waived_questions`（题号和能力证据），不冒充完成 |
| `waived_requirements` | 已作答题目中，经需求调整免除的非核心要求、题号和既有证据；保留实际未修改事实，不冒充该细节已经实现。只有核心行为已验证后才能调整验收 |
| `project_verified` | 项目核心验收项已全部核实才为 true；运行骨架不能设为 true |
| `actual_minutes` | 已知实际时长的累计值；未知为 null，缺失部分用 `minutes_note` 说明；补充同一次反馈时替换原值后重算，不重复累加 |
| `blockers` / `feedback` | 当前卡点和最新结论，详细依据留在历史中 |
| `verified_days` | 只放达到核心要求的主线主题编号；应与对应单元“已验收”及项目验证一致。合并学习也逐主题核实，不能批量默认通过 |
| `skills` | 按知识点建对象，包含 `level`、`evidence_session_ids`、`review_next`；等级为未评估、需补练、需提示、可独立。尚未评估时可不建条目 |
| `sessions` | 每次实际学习反馈一项：`id`、`date`、`learning_day`、`source`、`submitted_questions`、`actual_minutes`（未知 null）、`help_level`（独立/提示/完整答案/未知）、`checks`、`decision`。checks 记录验证方式、命令或来源及真实结果，不能只写通过 |
| `planning.last_reviewed_at` | 最近一次实际学习反馈日期；路线初始化不填验收日期 |

状态回退和新增技能必须有反馈编号支持。同一次提交的补充更新原 session 和原反馈条目；新的尝试新增编号并保留旧结果。
主题可以通过核心能力诊断免做同类题，但必须在对应 `days` 中记录 `waived_questions` 和验收依据，不能默默跳过。

此机制由能访问项目文件的助手在本轮交互中执行，不包含后台程序。换聊天时先读取这些文件；其他环境访问不了本机时，需要用户提供材料，不能声称已同步或写入。
