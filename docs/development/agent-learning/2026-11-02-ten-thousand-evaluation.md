### 精准回答的核心设计

现有_render主要检查段落、已读引用及数字，不能证明每项问题都被覆盖，也不能证明“引用了某个已读字段”就使用了正确指标。建议复用FactProjection已有name/window/kind/status/value/presentation字段，新增问题目标与事实之间的绑定和覆盖校验。

1. **先保留问题片段，再建立原子诉求。** 在现有路由请求内同时输出问题片段对应的目标，区分报告指标、客服主题、整份总结及无法确认的片段。程序验证片段确实来自已通过隐私检查的问题；用当前报告的受控指标别名、周期/次数/机构口径与高置信客服表达做独立交叉核对。不能只信模型自己列出的目标清单，否则漏问可能从第一步就被隐藏。否定、改口、引用和历史诉求要保留关系，不能见到“退款”等词就机械新增退款主题。

2. **先识别诉求，再绑定真实来源。** 路由阶段继续不附报告正文或目录，不要求它凭空编造field_ref。报告目标进入既有受控目录/工具流程后，才绑定本报告的已暴露字段引用、指标口径和周期；未暴露引用、其他报告标识或原始路径继续拒绝。案件金额与借贷未结清区间即使都含“金额”，也不是同一个目标。

3. **每项目标都要有本地确定的处理状态。** 在内部区分未查询、已确认、真缺失、null/空白、展示规则未知或被限制，以及仍有歧义。复用现有provided/missing/null/empty/withheld事实状态，不把它们压成单一“无法确认”。未查询是执行状态，不能由模型改写为报告缺失；客服政策未核实与报告字段缺失也应分别表达。达到预算仍未覆盖时，对具体未完成项给出明确说明，不补造答案。

4. **事实由程序固定，AI组织解释。** 建议结论按目标提交内部结构：目标引用、实际来源、回答类型和必要解释。数值、单位、周期、范围和缺失状态由程序依据已核验展示结果组装，AI不自由重写事实；服务事项由已登记本地主题组合。最后验证目标覆盖、来源语义、事实值与回答一致，而不只验证sources数组存在。最终用户仍看到自然简短中文，不显示内部引用、状态枚举、工具或JSON。

5. **核对目标清单和最终回答两个环节。** 既检查“每个目标都有结果”，也检查“原问题中每个实质诉求都进入目标”。对语义歧义仅在会影响答案时澄清，已明确的问题直接回答；追问只复用同一报告的授权引用和口径，值仍按既有出口读取。默认复用原路由请求和本地校验，不为每个问题再增加一次独立模型审稿，保持现有请求与工具预算。

6. **模块总结和全报告总结分开授权范围。** 局部批次只给本模块结论，不据局部缺失推断整份报告可用范围。全局可用模块范围由程序给出受控元信息，跨模块结论只在最终阶段产生。对未提供或withheld字段按其真实含义给本地短说明，避免缺失模块的自由发挥污染其他模块。
