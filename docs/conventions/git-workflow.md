# 项目级 Git 提交与合并规范

本规范适用于本 Git 仓库内所有子项目、语言和分支，包括代码、文档、配置及项目技能文件。
根目录 `AGENTS.md` 和 `CLAUDE.md` 统一引用本文件，子项目工具继续按实际技术栈使用。
用户当前明确要求优先；提交、推送、创建或更新 PR/MR、合并等操作遵循用户已有授权，已有授权无需重复确认。

## 提交范围和信息

- 一次提交对应一个可说明、可验证的需求，不混入其他任务、临时调试或无关格式化。
  同一需求可以包含相关代码、测试、开发记录、接口说明及配置示例；多个子目录属于同一个 Git 仓库。
- 先检查当前分支、工作区和暂存区，按文件或补丁暂存本次内容。不得使用全量暂存混入其他任务，
  不擅自清空暂存区、覆盖文件、切换分支或清理用户已有改动。
- 标题统一为 `type(scope): 中文说明`，描述实际行为，避免“更新代码”“修改问题”等含糊表述。
  `type` 使用下表；`scope` 使用 `agent-learning`、`neighbor-help`，或表示公共规范、工具的 `project`。
  需求涉及多个子项目的公共改动使用 `project`；未来子项目使用其目录名。
- 正文用中文说明原因、主要改动、实际验证及限制，技术标识和命令保留原文；不把未执行的检查写成通过。
  不在提交内容或信息中包含密钥、token、真实验证码、个人报告或本机私有配置。
- Git 自动生成的 merge/revert 信息可保留标准标题，补充中文原因和验证说明；其差异仍须通过检查。

| type | 使用范围 |
|---|---|
| `feat` | 新增功能 |
| `fix` | 修复缺陷 |
| `refactor` | 不改变预期行为的重构 |
| `docs` | 文档及开发规范 |
| `style` | 不改变行为的格式调整 |
| `perf` | 性能优化 |
| `test` | 测试用例和测试支持 |
| `build` / `ci` | 构建依赖、构建流程或 CI |
| `chore` | 其他维护工作 |
| `revert` | 撤销已有变更 |

示例（验证内容按本次实际执行情况填写）：

```text
docs(project): 统一项目级提交与合并规范

原因：各子项目需要统一的提交格式和检查要求。
改动：增加公共规范，并接入项目规则入口。
验证：已检查文档链接和差异空白；业务代码未变更。
```

## 所有分支提交前检查

普通提交、`git commit --amend`，以及 cherry-pick、rebase、merge 等生成或替换提交的操作均适用。
对批量生成提交的操作，先在临时检出或集成分支准备并检查将生成的各提交及最终结果，检查前不更新目标分支。

1. 读取适用的项目规范和子项目说明，明确需求、目标分支、检查命令与提交范围。
   先运行 `git branch --show-current`、`git status --short`、`git diff --cached --name-status` 和
   `git diff --cached`，逐个检查新增、修改、删除、重命名及文件模式变化。
2. 普通提交检查暂存区相对 `HEAD` 的全部差异；首次提交使用空树为基点。
   amend 检查最终替换提交相对其父提交的完整差异，不能仅检查本轮新增的暂存内容。
   merge 结合各父节点和解决冲突后的结果检查，不能因默认合并差异为空而跳过。
3. 记录 `HEAD`、提交父节点、`git write-tree` 得到的暂存树 SHA，以及适用规范的 Git SHA 或内容摘要。
   用 `git show :<path>` 等方式读取实际暂存内容，不能用工作区中的修复证明暂存内容合规。
4. 对检查快照逐项核对适用规则，包括中文职责与关键逻辑注释、命名、接口契约、异常处理、敏感信息、
   架构复用及文档同步。全部检查范围均需覆盖，不能只按某一种源码扩展名筛选。
   Java 规则仅在目标技术栈适用时使用，不套用到 Python 或前端文件。
5. 执行与改动匹配的现有格式检查、lint、静态检查、编译及必要测试或关键路径验证。
   普通提交运行 `git diff --cached --check`；amend 及其他操作对最终提交范围执行等价空白检查。
   工作区与暂存区不一致时，依赖文件内容的检查在准确暂存快照的临时检出中执行；无法验证则阻断。
   纯文档变更检查链接、结构、规范一致性和空白，不要求运行无关业务构建或新增只核对文案的测试。
6. 按根目录开发规范维护对应开发记录；接口、配置和使用方式变化时同步受影响文档。
   公共规范或工具的记录写入 `docs/development/project/`，业务需求写入对应子项目目录。
7. 只有必要检查全部完成、零违规且零待确认项才允许继续。修复后只暂存本次相关补丁，重新检查完整范围。
   执行提交前再次核对 `HEAD`、父节点、暂存树 SHA 和规范版本；任一变化都使旧结论失效。

检查规范不要求提交时整个工作区干净；其他任务改动应保留在原处，并与本次提交内容隔离。
不要直接执行未经检查的组合提交脚本，尤其是包含 pull、全量暂存或 push 的脚本。

## 推送与 PR/MR 检查

普通分支推送前核对远端、实际源 SHA 及将推送的全部提交，补齐相应提交检查证据；
本地已经提交不等于已经通过规范检查。使用明确的远端和分支，不隐式推送其他分支。

创建、更新或合并 PR/MR 前，必须检查来源相对最新目标分支的完整有效差异，草稿 PR/MR 同样适用。
目标包括 `main`、`master`、`test` 以及实际使用的发布或集成分支；其他目标也执行相同差异检查。

1. 先获取最新远端引用，明确 `目标 <- 来源`，记录远端、双方完整 SHA 和 merge-base。
   无法更新远端、确定基线或确认实际源版本时，不使用过期本地分支代替。
2. 检查 `git diff <merge-base> <source-sha>` 的全部文件与补丁，执行上一节适用的规范和验证。
   不以最后一个提交、少数新增行或尚未推送的工作区修复代替 PR/MR 的真实内容。
3. 推送后核对远端源 SHA；创建后核对 PR/MR 实际来源、目标及比较基点。
   更新和合并前再次核对源 SHA、最新目标 SHA、merge-base 与规范版本。
   源码、目标分支、格式化结果或规范发生变化后重新检查完整差异。
4. 检查通过后，继续已获授权的操作；提交检查不能替代 PR/MR 检查，PR/MR 检查不能替代合并门禁。

## 分支合并门禁

任何 merge、会整合历史的 pull、PR/MR 合并或跨分支推送，操作前必须满足下列要求。
无冲突不代表可以安全合并，缺少检查证据不得继续。

1. 先执行 `git fetch <remote> --prune`；确认工作区干净，记录 `目标 <- 来源` 和双方 SHA。
   存在其他任务未提交改动时使用独立 worktree，不自动 stash、清理或覆盖这些改动。
2. 使用 `git merge-base`、`git merge-base --is-ancestor`、`git log <target>..<source>` 及
   `git log --first-parent --merges` 检查祖先关系、独有提交和历史合并。
   来源历史中的合并逐个检查父节点及 `git diff <merge>^1 <merge>`，不能仅凭分支名或提交标题判断归属。
3. 检查 `git diff <target>...<source>`，确认没有混入其他需求或版本补丁。
   出现混入时先明确本次目标补丁，重建独立分支或补丁；不要盲目 merge/revert。
   只有需要改变用户已授权范围或无法判断改动归属时才请求补充信息。
4. 使用 `git merge-tree --write-tree <target> <source>` 或一次性集成分支模拟合并，检查冲突、
   文件数量、异常目录、大批删除、配置、SQL 和需要保留的目标分支改动。
5. 正式合并前保留可恢复的 SHA 或备份引用，在集成分支完成检查，禁止改写共享历史和 force push。
   受保护分支默认走 PR/MR；直接推送需用户在看到检查证据后明确授权。
6. 合并后重新执行相关验证和 `git diff --check`；若已获授权推送，则 fetch 核对远端目标 SHA。
   跨分支清理或 revert 还须证明：非预期补丁已清除，目标分支原有改动均保留。

## 检查结论和交付证据

| 结论 | 判定及后续操作 |
|---|---|
| `PASS` | 适用检查全部完成、零违规、零待确认，内容与规范版本仍一致；可继续已授权操作 |
| `FAIL` | 存在任一明确违规；禁止继续相应提交、推送或 PR/MR 操作，修复后复查 |
| `BLOCKED` | 无已确认违规，但规范、环境或版本证据不足，或必要检查未完成；补齐后重新检查 |

违规与未完成检查同时存在时使用 `FAIL`，并列出所有未完成项。
不得以“轻微”“只是警告”“先提交再改”跳过适用规则；不适用的检查写明理由。
检查报告在交付说明或现有开发记录中保留，包含操作范围、分支与版本证据、适用规范、实际命令和结果、
问题的文件与行号、修复状态及未完成项；不要为每次检查反复创建开发记录。

本次接入的是项目文件和代理执行约定，未安装 Git hooks 或远端 CI/分支保护。
自动化拦截是否生效需要对应工具实际接入并验证，不能仅凭本文件或已安装技能宣称生效。
