# 开发记录和接口文档

项目根目录是文档归档基准。当前开发写入 `docs/development/<子项目>/`，接口说明写入
`docs/interfaces/<子项目>/`。已有 `docs/superpowers/` 历史文档保留原路径，必要时建立链接。

每次实际开发都应有可回溯记录，包括功能、缺陷、配置、注释及规范调整。
一次需求对应一份持续维护的记录；关联的注释完善和规范建设可以共用一份记录。
未知信息写明未核实，内容规模与改动匹配，不填充无关的发布、SQL 或部署章节。

## 开发记录最小内容

```markdown
# 本次开发主题

- 日期：实际开发或补录日期；补录时注明历史证据来源。
- 范围：本次涉及的子项目、功能或目录。
- 状态：进行中、已完成，或部分完成及具体未完成项。

## 需求与原因

用户希望的行为、原有现象以及核实后的根因；没有缺陷则写开发目标。

## 方案与改动

最终调用流程、关键规则、涉及文件及它们为什么需要修改。
记录相关接口、配置和注释更新；复杂改动再补充取舍。

## 验证

| 检查 | 命令或方式 | 实际结果 |
|---|---|---|
| 相关检查 | 实际执行的命令或操作 | 通过、失败或未执行及原因 |

区分当前执行与引用历史证据；说明模拟测试与实连的覆盖范围。

## 使用与限制

如何运行或配置、已知限制、未完成验证及后续需要的信息。
仅有实际影响时记录发布或恢复步骤，不虚构提交号、上线状态和负责人。
```

## 接口说明最小内容

同一功能维护一份说明，保持与代码一致：

- 调用方、现有服务、HTTP 方法和含服务前缀的路径。
- 鉴权头、参数类型及位置（查询串、JSON、表单），必填条件及业务意义。
- HTTP 与业务成功条件、调用方消费的响应字段、使用虚构值的最小示例。
- 错误处理、重试行为和环境限制；只记录实际实现，不把未来计划写成现状。
- 验证日期、实际覆盖情况，以及后端完整协议尚未核实的部分。

配置和运行方式在子项目 README 中维护，开发记录链接到它，避免复制长段说明后产生漂移。
